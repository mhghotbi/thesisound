MVP Verdict

NOT READY — CORE GAPS

Thesisound از نظر معماری مسیر کاملی دارد، اما شواهد runtime فقط رسیدن تا script_verified را نشان می‌دهند. فایل صوتی نهاییِ قابل پخش برای پروژه‌های جاری وجود ندارد و کنترل coverage نیز می‌تواند حذف مفاهیم مرکزی را سالم اعلام کند.

نتیجه‌ی تصمیمی: محصول برای release محدود به کاربر واقعی هنوز آماده نیست. با تمرکز روی سه مسیر digital، اصلاح coverage/verifier و اثبات audio قابل تحویل، می‌تواند به یک MVP کوچک ولی کامل تبدیل شود.

۱. MVP واقعی محصول

ارزش اصلی محصول تعداد stageها نیست؛ یک اپیزود فارسی قابل اعتماد و واقعاً شنیدنی است:

موضوع یا منبع ← استخراج معتبر ← انتخاب و سازمان‌دهی مفاهیم مهم ← script فارسی شنیدنی ← فایل صوتی قابل پخش و دانلود

این مسیر در design و serviceها وجود دارد، ولی end-to-end فعلی اثبات نشده است: دو پروژه‌ی جاری تا script موفق‌اند، درحالی‌که هیچ‌کدام audio نهایی ندارند. تنها audio ثبت‌شده در archive شامل metadata، ASR و QA JSON است؛ خود final.wav یا final.mp3 در repo موجود نیست.

۲. Product Value

ارزیابی فعلی: Weak value — با ظرفیت رسیدن به Acceptable MVP value

تمایز واقعیevidence excerpt، locator، source binding، duration gate و امتناع از padding مزیتی معنادار نسبت به summary ساده‌اند.
اعتماد هنوز شکننده استاپیزود ۲۰ دقیقه‌ای درباره‌ی The Human Condition مفاهیم مرکزی action، plurality و natality را حذف کرده، اما coverage آن را well_covered و verifier همه‌ی ابعاد را ۱٫۰ اعلام کرده است.
فارسی قابل فهم ولی نوشتاریجمله‌ها متراکم و طولانی‌اند؛ سؤال‌وجواب‌ها گاهی مصنوعی و شبیه prompt پاسخ‌دهی LLM هستند، نه گفت‌وگوی مناسب شنیدن.
تنوع محصول اثبات نشدهفقط نمونه‌های ۱۰ و ۲۰ دقیقه‌ای در mode توضیحی داریم؛ تفاوت معنایی durationها و چهار content mode با artifact واقعی نشان داده نشده است.

So what: اگر fidelity و coverage قابل اعتماد نشوند، پیچیدگی provenance برای کاربر به مزیت واقعی تبدیل نمی‌شود و استفاده از یک LLM عمومی همچنان انتخاب ساده‌تر خواهد بود.

۷. Cost per Episode

هزینه‌ی دقیق episode قابل محاسبه نیست: اکثر callها به Okian route شده‌اند، Okian نرخ عمومی ندارد، ledger همه‌ی callها را synthetic ثبت کرده و search/OCR/ASR/infrastructure نیز قیمت کامل ندارند. تنها کف قابل اتکا، TTS صوتی است.

Cost / Performance Verdict: برای شروع بدون paid subscriber، معماری فعلی به‌اندازه‌ی کافی قابل پیش‌بینی یا ارزان نیست. مسئله‌ی اصلی TTS نیست؛ call count، rerun و provider بی‌قیمت‌اند.

۸. Recommended MVP Scope

Keep for MVP

  • upload-first برای English/Persian digital PDF و EPUB؛
  • brief کوتاه inline، parse-quality check و document map فقط برای سند بلند؛
  • evidence extraction، excerpt/locator validation، claim prioritization و provenance؛
  • plan coverage واقعی، script فارسی، deterministic checks و verifier کالیبره؛
  • TTS، فایل playable/downloadable، cache و retry/resume امن.

Simplify / Change before MVP

  • فقط mode توضیحی و دو مدت ۱۰ و ۲۰ دقیقه؛ تغییر duration نباید corpus را دوباره تحلیل کند.
  • corpus confirmation و شروع audio بمانند؛ plan approval فقط هنگام warning.
  • verifier یک‌بار روی script نهایی؛ reviser فقط در پاسخ به failure مشخص.
  • evidenceها batch شوند و وضعیت verified audio فقط پس از validation واقعی استفاده شود.

Defer until real users

  • Persian scanned PDF و OCR production؛
  • web discovery و authority ranking گسترده؛
  • critical، comparative و debate و مدت‌های ۳۰/۴۵/۶۰ دقیقه؛
  • full cross-source reconciliation و disagreement graph؛
  • infrastructure مربوط به scale و benchmarkهای challenge گسترده.

۹. Next Actions

۱. سه fixture واقعی را تا MP3 به release gate تبدیل کن Effort: M

Why: English PDF، Persian PDF و long document هنوز end-to-end اثبات نشده‌اند.

Expected impact: رفع بزرگ‌ترین ریسک release و مشخص شدن failure UX واقعی.

۲. coverage را روی plan/script و must-not-be-lost items اعمال کن Effort: M

Why: وجود claim در ledger امروز با حضور آن در اپیزود اشتباه گرفته می‌شود.

Expected impact: جلوگیری از حذف مفاهیم مرکزی با وضعیت سالم.

۳. verifier را با نمونه‌های human-reviewed فارسی کالیبره کن Effort: M

Why: امتیازهای کامل فعلی unsupported inference، repetition و نثر غیرشنیدنی را تشخیص نمی‌دهند.

Expected impact: افزایش source fidelity و کیفیت شنیداری.

۴. audio prerequisites و معنای verified را اصلاح کن Effort: S

Why: FFmpeg غایب، ASR خاموش و manual review قابل پذیرش است.

Expected impact: خروجی واقعاً قابل پخش و قابل اعتماد.

۵. تست‌های شکست‌خورده‌ی runtime پشتیبانی‌شده را صفر کن Effort: M

Why: اجرای audit برابر ۹۷۸ pass، ۲۱ fail و ۱ skip بود؛ failureها audio، login/UI، upload و contractهای دیگر را شامل می‌شدند.

Expected impact: کاهش دخالت فنی و failure نامفهوم برای کاربر.

۶. evidence batching، conditional reviser و reuse در تغییر duration را اعمال کن Effort: M

Why: بیشترین waste قابل رفع در همین سه نقطه دیده می‌شود.

Expected impact: کاهش محسوس cost، latency و rerun.

۷. UI نسخه‌ی اول را به upload-first، explanatory 10/20 و دو approval ضروری محدود کن Effort: S

Why: تنظیمات و gateهای فعلی پیش از اثبات value اصطکاک ایجاد می‌کنند.

Expected impact: onboarding ساده‌تر و release کوچک‌تر ولی کامل.

۱۰. شواهد و محدودیت‌های تصمیم

  • artifactهای جاری: script ده‌دقیقه‌ای و script بیست‌دقیقه‌ای.
  • شاهد coverage: coverage report در کنار must-not-be-lost review.
  • وضعیت benchmark: PRE-FREEZE-READINESS — freeze مجاز نیست و gold تولید نشده است.
  • تنظیمات هزینه و مدل: model routing و model pricing.
  • قیمت provider: Gemini API pricing و Google Search grounding pricing.

عدم وجود binary صوتی مانع ارزیابی مستقل pronunciation و prosody شد. برآورد هزینه‌های Google-equivalent سناریوی مقایسه‌ای است، نه invoice واقعی Okian. تست‌ها در محیط audit با Python 3.14 اجرا شدند؛ CI repo از Python 3.12 استفاده می‌کند.

پاسخ نهایی: امروز باید coverage، verifier، audio delivery و سه happy path دیجیتال حتماً درست شوند. ingestion، provenance، budget gate، cache و ساخت script همین حالا پایه‌ی کافی دارند. OCR فارسی، modeهای متعدد، reconciliation کامل و architecture مربوط به scale زودتر از نیاز واقعی ساخته شده‌اند.
